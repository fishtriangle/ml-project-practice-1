## О проекте

Работа разделена на три стадии, каждая — отдельный ноутбук в папке `project_notebooks/`.
Финальная цель — по результатам обследования предсказывать итог наблюдения пациента
(жив / трансплантация / умер).

**Стадия 1 — анализ данных** (`Stage_1_analysis.ipynb`): полный цикл разведочного анализа
медицинского датасета о пациентах с первичным билиарным циррозом. Проверяется качество данных,
выполняется очистка от клинически невозможных значений, выявляются статистические и клинические
закономерности. Практический результат — **отбор 15 признаков для модели** по трём основаниям:
дублирование (правило «одна информация — один столбец», блок 2.5), отсутствие связи с исходом
(блок 3.13) и «подглядывание в ответ» (блоки 3.10, 3.13). В конце стадии сохраняются два файла:
`data/processed/train_clean.parquet` (полный артефакт данных, 30 столбцов) и
`data/processed/train_model.parquet` (матрица из 15 признаков модели и цели).

**Стадия 2 — проверка применимости линейной регрессии** (`Stage_2_regression.ipynb`):
проверяется **возможность** применения оценки по числу (линейной регрессии) к задаче предсказания
клинического статуса. Проверяются четыре предпосылки метода без обучения модели; вердикт —
линейная регрессия неприменима из-за категориальной цели. Стадия читает `train_model.parquet`.

**Стадия 3 — модель предсказания исхода** (`Stage_3_classification.ipynb`): многоклассовая
логистическая регрессия как корректный ответ на категориальную цель. Основная часть — работа с
дисбалансом классов (`CL` — 3.5 % наблюдений): русские названия и разбор метрик, подбор порога
решения для редкого класса, веса классов, downsampling и upsampling, сравнение всех вариантов
между собой и контрольный опыт по периоду наблюдения. Стадия читает `train_model.parquet`.

## Датасет

- **Название:** Multi-Class Prediction of Cirrhosis Outcomes
- **Источник:** Kaggle Playground Series S3E26
  (https://www.kaggle.com/competitions/playground-series-s3e26)
- **Первоисточник:** UCI Machine Learning Repository, *Cirrhosis Patient Survival Prediction*
- **Объём:** 7 905 строк × 19 столбцов (пропусков нет)
- **Целевая переменная:** `Status` с тремя классами
  - `C` — пациент жив на момент окончания наблюдения (цензурирован) — 4 965 (62.8 %)
  - `CL` — пациент жив благодаря трансплантации печени — 275 (3.5 %)
  - `D` — пациент умер — 2 665 (33.7 %)
- **Признаки:** возраст, пол, принимаемый препарат, лабораторные показатели
  (билирубин, альбумин, медь, щелочная фосфатаза, AST, холестерин, триглицериды,
  тромбоциты, протромбиновое время), клинические признаки (асцит, гепатомегалия,
  сосудистые «паучки», отёки), гистологическая стадия фиброза, период наблюдения.

## Признаки модели: итоговый состав

Из 30 столбцов очищенного датасета в модель идут **15** (файл `train_model.parquet`):

| Группа | Признаки |
|---|---|
| Лабораторные показатели в логарифме | `log_Bilirubin`, `log_Copper`, `log_Alk_Phos`, `log_SGOT`, `log_Cholesterol`, `log_Tryglicerides` |
| Лабораторные показатели без преобразования | `Albumin`, `Platelets`, `Prothrombin` |
| Демография и стадия | `Age_years`, `Stage` |
| Клинические признаки | `Edema_num` (0 / 0.5 / 1), `Sex_M`, `Hepatomegaly_Y`, `Spiders_Y` |

Отсечены по трём основаниям (обоснование — блоки 2.5, 3.10, 3.12, 3.13 стадии 1):

| Основание | Столбцы |
|---|---|
| Дублируют выбранный вариант того же факта | `Bilirubin`, `Copper`, `Alk_Phos`, `SGOT`, `Cholesterol`, `Tryglicerides`, `Age`, `Edema`, `is_severe`, `Ascites` |
| Не связаны с исходом / технический | `Drug`, `id` |
| «Подглядывание в ответ» | `is_dead` (это `Status == 'D'`), `N_Days` (период наблюдения) |

**Решение по периоду наблюдения (`N_Days`).** Период — сколько дней пациент состоял под
наблюдением до развязки — сильно связан с исходом, но связь работает в обратную сторону: исход
определяет период, а не наоборот. Проверки стадии 1: приравнивание периода к максимальному не
меняет ни одного исхода; при одном и том же периоде встречаются все три исхода; интервалы
классов перекрываются. Двухэтапная схема (сначала исход, потом период) также отклонена: период
объясняется клиническими данными лишь на 22 %, знание исхода добавляет ещё 0.8 процентного
пункта. Контрольный опыт стадии 3 подтвердил числами: добавление периода меняет метрики на
тысячные доли — уровень шума. **Период в модель исхода не входит**; он остаётся в
`train_clean.parquet` для анализа выживаемости.

## Стадия 2 — проверка применимости линейной регрессии (`Stage_2_regression.ipynb`)

**Цель:** проверить **возможность** применения оценки по числу (линейной регрессии) для
предсказания клинического статуса пациента (`Status`) по результатам обследования.

**Формат раздела — необходимый минимум:** проверка четырёх предпосылок метода и вывод. Обучение
модели, метрики качества, интерпретация коэффициентов и логистическая регрессия вынесены в
стадию 3: линейная регрессия — инструмент для непрерывных целей, и проверка предпосылок
показывает несоответствие ещё до всякого моделирования.

| Блок | Содержание |
|------|-----------|
| **1. Импорты и настройки** | numpy, pandas |
| **2. Загрузка данных** | Чтение `data/processed/train_model.parquet` (выход Stage 1: 15 признаков + цель), кодирование цели `Status` → `C=0, CL=1, D=2` |
| **3. Подготовка признаков** | Матрица = все столбцы файла, кроме цели; дополнительного кодирования не требуется (решения по признакам приняты на стадии 1) |
| **4. Быстрая оценка применимости** | 4 проверки-предпосылки за секунды без обучения модели: тип цели, линейная связь с целью (Пирсон), линейность связи (Пирсон против Спирмена), взаимная близость признаков |
| **5. Выводы** | Ответ на вопрос задачи, глоссарий терминов |

**Результат (числа):**

| Предпосылка | Что показали метрики | Вывод |
|---|---|---|
| Непрерывность цели | 3 значения (0/1/2) | **грубо нарушена** — это и есть причина отказа от метода |
| Линейная связь с целью | максимум \|r\| = 0.534 (`log_Bilirubin`) | сигнал есть, признаки информатны |
| Линейность связи | разрыв Пирсона и Спирмена ≤ 0.024 | выполнена (спасибо лог-преобразованиям стадии 1) |
| Взаимная близость признаков | ни одной пары \|r\| > 0.6; сильнейшая `log_Bilirubin ↔ log_Copper` = 0.538 | выполнена |

Отказ относится к выбору метода, а не к качеству данных: корректный инструмент — многоклассовая
логистическая регрессия, реализована в стадии 3.

## Стадия 3 — модель предсказания исхода (`Stage_3_classification.ipynb`)

**Цель:** построить корректную модель предсказания `Status` и разобраться, как дисбаланс классов
влияет на выбор метода обучения и метрик. Класс `CL` — 275 строк (3.5 %), в контрольной выборке
всего 69.

**Логика стадии:** сама логистическая регрессия обучается за доли секунды, поэтому содержательная
часть — не модель, а обращение с редким классом: почему доля верных ответов обманчива, как
настраивать порог решения в мультиклассовой задаче и чем `class_weight` отличается от
сэмплирования.

| Блок | Содержание |
|------|-----------|
| **1. Импорты и настройки** | scikit-learn (модель, метрики, разбиение, масштабирование), matplotlib/seaborn |
| **2. Загрузка данных** | Чтение `data/processed/train_model.parquet` (15 признаков + цель), анализ дисбаланса; цель **не** кодируется порядково, в отличие от стадии 2 |
| **3. Подготовка признаков** | Матрица = 15 отобранных признаков; напоминание оснований отбора (стадия 1) |
| **4. Разбиение и стандартизация** | Стратификация по `Status` (75/25, `random_state=42`), `StandardScaler` с `fit` только на train |
| **5. Базовая модель** | Многоклассовая логистическая регрессия (softmax), отчёт по классам, матрица ошибок, русские названия метрик |
| **6. Период наблюдения** | Обоснование исключения: период — следствие исхода; **контрольный опыт** (модель с периодом: доля верных ответов 0.7967 против 0.7951 — разница на уровне шума); двухэтапная схема и её слабость (R² 0.225 → 0.234) |
| **7. Порог решения для `CL`** | One-vs-rest вероятность класса `CL`, перебор порогов, графики полноты/точности/F-мера, матрица ошибок при выбранном пороге |
| **8. Веса классов** | `class_weight='balanced'`, сравнение с базовой моделью |
| **9. Сэмплирование** | Ручные `downsample` / `upsample` на numpy (эквиваленты `RandomUnderSampler` / `RandomOverSampler`); применяются только к обучающей части и только после разбиения |
| **10. Сводное сравнение** | Шесть вариантов в одной таблице, выбор лучшего по каждой метрике с явным указанием направления оптимизации |
| **11. Интерпретация коэффициентов** | Топ-12 признаков по модулю коэффициента, разрез по классам, знаки, свободные члены |
| **12. Выводы** | Ответ на задачу, глоссарий терминов |

**Результат:** базовая модель даёт долю верных ответов 0.795 при лог-потере 0.544, но полнота
класса `CL` равна 0.014 — из 69 пациентов с трансплантацией найден 1. Разница между долей верных
ответов (0.795) и средней долей верных по классам (0.532) — прямой диагноз дисбаланса.

| Вариант | доля верных ответов | ср. доля верных по классам | F-мера (ср. по классам) | F-мера (взвеш.) | лог-потеря | полнота CL |
|---|---|---|---|---|---|---|
| базовая | 0.795 | 0.532 | 0.532 | 0.779 | **0.544** | 0.014 |
| + период наблюдения (контроль, нелегально) | 0.797 | 0.533 | 0.534 | 0.781 | 0.540 | 0.014 |
| порог `CL = 0.07` | 0.730 | 0.586 | **0.549** | 0.752 | **0.544** | 0.348 |
| `class_weight='balanced'` | 0.695 | 0.589 | 0.537 | 0.738 | 0.780 | 0.391 |
| downsampling | 0.680 | **0.595** | 0.530 | 0.724 | 0.881 | **0.449** |
| upsampling | 0.689 | 0.585 | 0.534 | 0.734 | 0.779 | 0.391 |

Лучший вариант зависит от метрики: для соревнования (лог-потеря) — базовая модель и вариант с
порогом (0.544); для равной цены всех классов (F-мера по классам) — порог `CL = 0.07` (0.549);
для максимального поиска редкого класса — downsampling (полнота 0.449), но ценой 90 % обучающих
строк и худшей калибровки. Строка «+ период наблюдения» приведена только как контрольный опыт:
использовать период в модели нельзя — он известен только после исхода.

## Установка и запуск

### 1. Установка зависимостей

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

Все необходимые пакеты (`phik`, `lifelines`, `ydata-profiling`, `scikit-learn`) уже перечислены в
`requirements.txt`. Библиотека `imbalanced-learn` не требуется — сэмплирование реализовано
на numpy, как описано в блоке 9 стадии Stage_3.

### 2. Авторизация в Kaggle

Перед первым запуском создайте API-токен на https://www.kaggle.com/settings/api
и сохраните его как `~/.kaggle/kaggle.json` либо выполните в ноутбуке:

```python
import kagglehub
kagglehub.login()
```

### 3. Скачивание датасета

В блоке **1.2** стадии Stage_1 раскомментируйте вызов `kagglehub.competition_download` —
архив будет распакован в `./data/`.

### 4. Запуск ноутбуков (по порядку)

```bash
jupyter notebook project_notebooks/Stage_1_analysis.ipynb
```

Выполняйте ячейки последовательно сверху вниз. В конце блока 3.14 Stage_1 сохраняет
`data/processed/train_clean.parquet` (полный артефакт данных) и
`data/processed/train_model.parquet` (матрица 15 признаков модели + цель).

```bash
jupyter notebook project_notebooks/Stage_2_regression.ipynb
jupyter notebook project_notebooks/Stage_3_classification.ipynb
```

Стадии 2 и 3 читают `train_model.parquet`, поэтому запускаются после Stage_1. Список признаков
задаётся один раз на стадии 1 — просочиться в модель дубликату или утечке физически некуда.

### 5. Streamlit-дашборд

Для запуска:

```bash
streamlit run cirrhosis_dashboard.py
```

Дашборд будет доступен на `http://localhost:8501`.

### 6. HTML-отчёт ydata-profiling

После выполнения блока **7** Stage_1 в корне проекта появится файл
`cirrhosis_eda_report.html` — откройте его в браузере.

## Ключевые выводы

### По анализу данных (Стадия 1)

1. **Данным можно доверять в целом:** пропусков нет, формальные IQR-выбросы — это реальные
   тяжёлые пациенты, а не ошибки ввода; удаление по правилу 1.5·IQR недопустимо, корректная
   стратегия — log-преобразование и устойчивые меры (MAD, percentile rank).
2. **Целевая переменная `Status` несбалансирована** — класс `CL` встречается редко
   (275 наблюдений, 3.5 %), что требует взвешенных метрик и стратификации при разбиении.
3. **Лабораторные признаки сильно скошены вправо** (`Bilirubin`, `Copper`, `Alk_Phos`,
   `SGOT`) — обязательны `log1p`-преобразования перед линейными моделями.
4. **Стадия фиброза согласуется с анализами и значимо влияет на выживаемость** (log-rank
   `p < 0.05`) — сильный прогностический признак.
5. **Действует правило «одна информация — один столбец»:** инженерные признаки (логи, возраст
   в годах, флаги) не несут новой информации, и в модель берётся ровно один вариант каждой
   пары; иначе одна и та же информация учитывается дважды и веса становятся ненадёжными.
6. **Из пары «асцит ↔ отёки» (корреляция 0.635) оставлены отёки:** кросс-валидация показала,
   что без асцита качество не меняется (0.7997 против 0.8000), а без отёков — падает.
7. **Период наблюдения (`N_Days`) исключён из модели исхода:** он известен только после
   наступления исхода (следствие, а не причина); двухэтапная схема «сначала статус, потом
   период» отклонена (период объясняется на 22 %, статус добавляет 0.8 п.п.).
8. **Неинформативные признаки отобраны формально** (блок 3.13): исключаются `id` (технический
   ключ) и `Drug` (φk = 0.013, χ² p = 0.053 — связь с исходом отсутствует, что заодно
   подтверждает корректность рандомизации). `Sex` (92.8 % одного значения) и `Ascites`
   (95.2 %) остаются: редкое значение не означает отсутствия связи с целью.

### По проверке линейной регрессии (Стадия 2)

9. **Линейная регрессия для этой задачи неприменима** — предпосылка о непрерывности цели
   грубо нарушена: `Status` принимает три значения, а модель выдаёт произвольные вещественные
   числа. Проверка заняла секунды и дала тот же вывод, что занял бы полный цикл моделирования.
10. **Данные при этом пригодны для моделирования:** признаки информатны (максимум \|r\| = 0.534
    у `log_Bilirubin`), связи почти линейны (разрыв Пирсона и Спирмена ≤ 0.024), близких пар
    между признаками нет (сильнейшая 0.538). Отказ относится к методу, а не к датасету.

### По модели предсказания исхода (Стадия 3)

11. **Доля верных ответов при дисбалансе вводит в заблуждение.** Базовая модель: 0.795, но
    средняя доля верных по классам 0.532 и полнота класса `CL` 0.014 (1 пациент из 69).
    Основная метрика сравнения вариантов — F-мера (средняя по классам), лог-потеря остаётся
    метрикой соревнования.
12. **Порог решения в мультиклассовой задаче настраивается через one-vs-rest.** «Сместить 0.5»,
    как в бинарной классификации, нельзя. Порог `P(CL) > 0.07` поднял полноту `CL` с 0.014 до
    0.348 и F-меру по классам с 0.532 до 0.549, не изменив лог-потерю; ценой — 210 ложных
    срабатываний и падение доли верных ответов до 0.730. Порог — это явный выбор потерь.
13. **`class_weight='balanced'` — самый дешёвый способ увидеть редкий класс:** полнота `CL`
    0.391 без потери данных, но лог-потеря ухудшается до 0.780 (модель теряет калибровку).
14. **Сэмплирование не улучшает линейную модель.** Downsampling даёт лучшую полноту `CL` (0.449)
    и наихудшую лог-потерю (0.881), потому что оставляет 618 из 5 928 обучающих строк; upsampling
    почти повторяет `class_weight` — для линейной модели это математически близкие приёмы.
15. **Исключение периода подтверждено числами:** контрольная модель с периодом выигрывает
    0.0016 по доле верных ответов (≈ 3 пациента из 1 977 — уровень шума), при этом становится
    неприменимой к новому пациенту.
16. **Выбор «лучшей» модели неразрывно связан с выбором метрики:** лог-потеря — базовая модель
    и порог; F-мера по классам — порог `CL = 0.07`; средняя доля верных по классам и полнота
    `CL` — downsampling. Единого правильного ответа вне постановки задачи не существует.
17. **Коэффициенты модели клинически осмысленны:** главные маркёры риска смерти — возраст
    (+0.389) и протромбин (+0.290); высокий билирубин снижает шанс «жив» (−0.475) и повышает
    шанс «умер» (+0.274); старший возраст снижает шанс трансплантации (−0.481) — пациенты чаще
    умирают, не дождавшись её.

## Методология анализа

Работа построена по классической схеме — от проверки качества к одномерному, многомерному и
сегментированному анализу, затем отбор признаков, проверка предпосылок базового метода и
корректная классификация:

- **Качество данных:** пропуски, дубликаты, биологически невозможные значения, клинические
  диапазоны, согласованность категориальных признаков, формальные статистические выбросы
  (IQR, z-score, MAD).
- **Одномерный анализ:** описательные статистики, гистограммы + KDE, violin/box, QQ-plot,
  тесты нормальности, частоты категориальных признаков.
- **Survival-специфика:** Kaplan-Meier кривые и log-rank тест по `Status` и `Stage`.
- **Многомерный анализ:** pairplot, корреляция Пирсона, матрица φk (phik) — универсальная мера
  связи для смешанных типов признаков, построенная на итоговом наборе 15 признаков.
- **Сегментированный анализ:** сравнение профилей стадий и групп исхода через radar chart
  на percentile rank.
- **Автоматизация:** ydata-profiling как чек-лист, Streamlit-дашборд для интерактивного
  исследования подгрупп.
- **Отбор признаков (стадия 1):** три основания — дублирование (правило «одна информация —
  один столбец» + кросс-валидация спорных пар), отсутствие связи с целью (φk, mutual
  information, Cramér's V с χ²-тестом, Kruskal-Wallis; решение по размеру эффекта, а не по
  p-value), утечка ответа (`is_dead`, `N_Days`).
- **Проверка предпосылок (стадия 2):** быстрая оценка применимости линейной регрессии через
  корреляционные метрики (Пирсон, Спирмен) и анализ взаимной близости признаков.
- **Классификация (стадия 3):** многоклассовая логистическая регрессия, сравнение методов
  работы с дисбалансом (порог решения, веса классов, сэмплирование) на одной
  стратифицированной контрольной выборке, интерпретация коэффициентов по классам.

## Ограничения работы

- **Данные синтетические** — сгенерированы моделью по мотивам реального датасета UCI. Редкие
  классы и хвосты распределений могут отличаться от реальной популяции пациентов.
- **Номинальная цель закодирована порядково только для проверки предпосылок** (стадия 2):
  промежуточных статусов не существует, и это одна из причин отказа от линейной регрессии.
- **Оценка на одном разбиении 75/25** (стадия 3): для устойчивых выводов требуется k-fold
  кросс-валидация; на стадии 1 кросс-валидация использована для решения спорной пары.
- **Прогноз, а не лечение:** причинный эффект препарата `Drug` не оценивался; период
  наблюдения исключён из модели как следствие исхода.
- **Лог-потеря варианта с порогом** не переопределяется: порог меняет правило вывода, но не
  вероятности модели.
